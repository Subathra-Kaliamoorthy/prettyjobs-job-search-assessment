# PrettyJobs — Job Search Application

A full-stack job search app: 1,200 generated job listings stored in PostgreSQL, served
through a backend API, and searchable from a React frontend.

- **Live app:** https://prettyjobs-job-search.ksuba-cf.workers.dev
- **Example API URL:** https://prettyjobs-job-search.ksuba-cf.workers.dev/api/jobs?q=nurse&limit=5
- **Full job detail:** https://prettyjobs-job-search.ksuba-cf.workers.dev/api/jobs/1

---

## Architecture

The frontend and the API are **one Cloudflare Worker**, not two deployments. Static assets
and `/api/*` share an origin, which removes CORS entirely and means there is a single URL
to deploy and share.

```
Browser
   │
   ▼
Cloudflare Worker ── /api/*      → Hono router
   │                 /job/123    → index.html (SPA route)
   │                 /assets/*   → static asset (Worker not invoked)
   ▼
Drizzle ORM → Neon PostgreSQL (1,200 jobs)
```

All searching, filtering, sorting and pagination happen **in SQL**. The browser never
receives more than one page of results.

## Technologies

| Layer | Choice |
|---|---|
| Frontend | React 19, TypeScript, Vite 8 |
| Styling | Tailwind CSS v4 |
| Routing | React Router 7 |
| API | Hono |
| Runtime | Cloudflare Workers (Static Assets) |
| Database | Neon PostgreSQL |
| DB access | Drizzle ORM + `@neondatabase/serverless` (HTTP driver) |

**Why the Neon HTTP driver rather than Cloudflare Hyperdrive:** Hyperdrive requires a
`wrangler hyperdrive create` step whose generated ID must be pasted into config, so the
project could not be reproduced from a clone alone — and its pooling/caching benefit is a
paid-plan feature. The HTTP driver needs no binding and no wrangler configuration.

## Setup

```bash
npm install

# 1. Create a free Neon project at https://neon.com, copy the pooled connection
#    string, and put the SAME line in two files (both are gitignored):
#
#    .env        -> read by drizzle-kit and the seed script (Node)
#    .dev.vars   -> read by Wrangler, exposed to the Worker as c.env.DATABASE_URL
#
#    DATABASE_URL="postgresql://user:pass@ep-xxx-pooler.region.aws.neon.tech/neondb?sslmode=require"

npm run db:push     # create the jobs table from db/schema.ts
npm run db:seed     # generate and insert 1,200 jobs

npm run dev         # http://localhost:5173 — SPA and API together
```

Other scripts: `npm run build`, `npm run typecheck`, `npm run preview`, `npm run deploy`.

## API

### `GET /api/jobs`

| Param | Example | Behaviour |
|---|---|---|
| `q` | `react` | Matches title, company or skills (case-insensitive) |
| `location` | `Bangalore` | Exact match |
| `jobType` | `full-time` | `full-time` / `part-time` / `contract` / `remote` |
| `experience` | `senior` | `entry` / `mid` / `senior` / `lead` |
| `minSalary` | `1500000` | Jobs whose band reaches at least this |
| `maxSalary` | `3000000` | Jobs whose band starts at or below this |
| `sort` | `newest` | `newest` / `oldest` / `salary_desc` / `salary_asc` |
| `page`, `limit` | `1`, `20` | `limit` capped at 100 |

```json
{
  "jobs": [{ "id": 1, "title": "Senior React Developer", "...": "..." }],
  "page": 1, "limit": 20, "total": 137, "totalPages": 7
}
```

### `GET /api/jobs/:id`

Returns the full job including `description`, or `404 {"error": "Job not found"}`.

## How the data was generated and stored

Job data was generated by a **deterministic TypeScript seed script** (`db/seed.ts`) using a
seeded `mulberry32` PRNG, drawing from a **hand-authored vocabulary** of 20 industries,
133 role templates, 145 companies and 598 distinct skills (`db/data.ts`).

The split is worth being explicit about:

| Layer | How it was produced |
|---|---|
| The vocabulary in `db/data.ts` | Written with **Claude Code** — industries, role templates, companies, skill sets, salary bands |
| The 1,200 job rows | Produced by **`db/seed.ts`**, which calls **no AI at runtime** — no network access beyond the database insert |

Running `npm run db:seed` reproduces the same 1,200 listings every time: it makes no model
calls, needs no API key, and costs nothing. The script draws its 1,200 rows from **178,950
reachable combinations** (industry × role × company × experience level × job type ×
location), before skill sampling, salary jitter and date skew multiply that further.

The rows are inserted into Neon in chunked multi-row inserts. Nothing is hard-coded in the
frontend and there is no JSON file — the API is the only source of job data.

The 20 industry bundles cover technology, healthcare, finance, education, retail,
manufacturing, construction, hospitality, logistics, legal, marketing, media, HR, sales,
customer support, agriculture, energy, public sector, pharma and skilled trades. Each bundle
owns its own companies, roles, skill vocabularies and salary bands.

Every job is generated **within a single bundle**, so a job is always internally coherent —
a Registered Nurse works at a hospital with nursing skills and a nursing salary, never at an
investment bank with Kubernetes listed as a skill. On top of that:

- **Experience level drives the title and the salary.** A base mid-level band is scaled
  (entry 0.55×, mid 1×, senior 1.6×, lead 2.3×) and jittered ±8% so bands are not identical
  across listings. Roles carry a `leadTitle` override where "Lead {title}" would read wrong
  — so the data contains *Nurse Manager*, not *Lead Registered Nurse*.
- **Role-constrained job types.** A welder is never remote; a backend engineer can be.
- **Recency-skewed posting dates** across the last 90 days, so "newest first" is meaningful.
- **Weighted round-robin across industries**, so every sector stays represented and filter
  combinations do not land on empty result sets. Technology carries a heavier weight (about
  18% of listings across 19 software roles — Software Engineer, Full Stack Developer, Java
  and Python Developer, DevOps, SRE, ML, QA, Security and more), matching how software roles
  dominate real job boards.
- **Posting dates are the one non-reproducible field** — they are anchored to the time the
  seed runs, so listings always look recent. Every other field is identical across runs.

"Skills" generalise across every industry as tags: `Patient Care`, `HACCP`, `MIG Welding`
and `Contract Drafting` sit in the same column as `React` and `Kubernetes`.

Workers against Pages, Hyperdrive against the Neon serverless driver, and to settle the

**Claude Code** — the implementation, working from that plan:

| Used for | Detail |
|---|---|
| Application code | Hono API, Drizzle schema and query layer, seed generator, React frontend, Tailwind UI |
| Job-data vocabulary | Authoring `db/data.ts` — 20 industries, 133 role templates, 145 companies, 598 skills, salary bands |
| Documentation checks | Verifying Cloudflare, Neon, Drizzle and Tailwind behaviour against their live docs rather than relying on model memory |
| Code review | Reviewing the finished code, which surfaced real bugs that were fixed before deploying |
| Deployment | Cloudflare Workers deploy and production secret configuration |

### Choices that came out of that

Three decisions worth calling out, because each reversed an obvious-looking default:

- **Neon HTTP driver instead of Hyperdrive.** Hyperdrive was the natural choice on paper and
  was in the original plan. Checking the current docs showed its pooling and caching are a
  paid-plan feature, and that it needs a `wrangler hyperdrive create` step whose generated ID
  must be pasted into config — meaning the project could not be run from a clean clone. The
  HTTP driver needs no binding and no wrangler configuration at all.
- **`run_worker_first: ["/api/*"]`.** By default Cloudflare treats a browser address-bar
  request as a navigation and answers `/api/jobs` with `index.html`, to avoid billable Worker
  invocations. Without this line the API link in this README would render the React app and
  look broken to anyone who clicked it.
- **Pinning `drizzle-orm` to the stable 0.45 line.** The Drizzle docs now serve v1.0 content
  whose install snippets read `drizzle-orm@rc`; copying them would have silently put a
  four-hour project on a release candidate.

No AI runs at application runtime or at seed time — see *How the data was generated* above.

## What I would improve with more time

- **Database indexes** — 1,200 rows scan in well under a millisecond, so indexes would be
  premature here. At real volume I would add a GIN index on `skills`, a trigram index for the
  `ILIKE` search, and a btree on `posted_at`.
- **Proper full-text search** — `ILIKE` has no relevance ranking. Postgres `tsvector` with
  `ts_rank` would order results by match quality rather than by date.
- **Keyset pagination** — `OFFSET` degrades on deep pages; a cursor on `(posted_at, id)` scales.
- **Tests** — unit tests for the pure helpers (`formatSalary`, `pageWindow`, the LIKE escaper,
  the integer clamp), integration tests over the API query builder, and an end-to-end run
  covering search → filter → detail.
- Multi-select filters, a salary slider, saved searches, and a skeleton loading state.

## Notes

- Neon's free tier scales the database to zero after ~5 minutes idle and this cannot be
  disabled, so the **first request after a quiet period takes about a second**. Subsequent
  requests are fast.
